# 0022: Plugins in TypeScript, on QuickJS and in a sandboxed iframe

Date: 2026-10-17, revised 2026-10-18 (Lua replaced by TypeScript before release). Status: accepted.

## Context

Operators want to add small features (a game corner, a companion fed by a desktop tool, office-specific gadgets) without forking Home Quarters. The first target is deliberately small: enough for a plugin to add a pet that follows its owner, apart from the built-in pets. Two constraints frame it. The world server is authoritative and must stay cheap: no per-frame traffic, bounded queues, no all-pairs work. And the page must not hand plugin code the session, the media devices or the DOM.

## Decision

- **A plugin is a folder** under `HQ_PLUGINS_DIR/bundled` or `HQ_PLUGINS_DIR/installed`, with a `plugin.json` manifest, optional server code and an optional `public/` folder. It is installed by the operator, never uploaded. Plugins are trusted code, and the limits below are about robustness, not hostile authors. An administrator enables or disables each plugin from the admin dialog. A plugin starts disabled; the choice is stored per office and audited, and it takes effect live.
- **Two sides, one reserved prefix.** `bundled/` ships in the image; `installed/` is the operator's, often a read-only volume mounted at `/app/plugins/installed` so the image's `bundled/` stays visible. Both are optional. Bundled plugins must be named `hq-*` and installed ones must not, checked on the folder and on the manifest name (routes and assets are served under the latter). This makes a collision impossible rather than detected: an image update adding a bundled plugin can never stop a plugin an office installed. Reserving the prefix before any office runs plugins avoids a migration later. A plugin refused for its name, or two claiming one name on the same side, is listed with the rule it breaks and never resolved by name. Nothing is ever written in a plugin folder: compiled code stays in memory, keyed by a fingerprint of the folder.
- **Typed code: TypeScript on both sides.** Server code (`main.ts`) and browser code (`public/client.ts`) are compiled by esbuild, a Go library, when the server scans the plugins, with the files they import. Imports must stay inside the plugin's folder (inside `public/` for the browser code): no packages. What is checked is the file actually read, after links and `package.json` fields, and only code files (`.ts`, `.tsx`, `.js`, `.mjs`, `.json`). The result is kept with a hash of the folder's contents and compiled again only when one changed. `plugins/sdk/server.d.ts` and `client.d.ts` type both globals; esbuild strips types without checking them, and the repository's gate runs `tsc` on the sample and the test plugin, so the declarations cannot drift. JavaScript works too.
- **Server code runs in QuickJS** (`modernc.org/quickjs`, pure Go, no cgo), with no I/O, timers or `require`. Each running plugin is one goroutine that owns its VM, fed by a bounded inbox (256), like the world. Each call has a 50 ms budget (QuickJS's interrupt; the promise jobs a call starts run right after it, with their own budget, so `async` code works), the top level and `load()` 1 s, and each plugin a 16 MB heap cap. A plugin over either, or over 10 errors a minute, is stopped and shown as crashed; errors name the function they came from. Recursion is capped at a few thousand calls: every JavaScript frame of the pure-Go QuickJS also costs Go stack, and a Go stack overflow would end the whole server. Only the known exports are allowed, so a misspelled one fails loudly. The frame sent to browsers is checked to be valid JSON on the Go side: a plugin replacing `JSON.stringify` cannot forge another protocol message. The module exports `load`, `update(dt)` (10 Hz), `onJoin`, `onLeave`, `onMessage` and `unload`; the global `hq` offers `send`/`broadcast`, `players`, `kv`, `route`, `log` and `now`. Arguments and results cross between Go and JavaScript as JSON. Builds with the race detector give calls ten times the budget (tests only): it slows the pure-Go QuickJS down by about that much.
- **Presence for plugins is visible presence.** The world reports `OnPresence(online)` when a member joins, leaves (after the grace), goes invisible or comes back. Invisible members are offline to plugins, as they are in the roster. `onJoin` is replayed for everybody online when a plugin starts.
- **Plugin traffic never costs a connection, in either direction.** A plugin frame is queued on the reliable path only while the recipient's queue is under half full; otherwise it is dropped and counted (`hq_plugin_frames_dropped_total`). Every recipient also has a budget of 10 plugin messages a second (burst 20, 4 KB each), shared by all plugins. Over it, `hq.send` and `hq.broadcast` return `false`: they do not raise, because an error would count toward the error limit, and a burst of joins or clicks by members could then stop the plugin. Towards the server, the page holds plugin messages to 8 a second (burst 16), under the socket's own bucket, so a plugin cannot earn its member strikes and a disconnection. Pending presence changes are coalesced per member, so the queue is bounded by the office size.
- **Browser side: a hidden iframe with `sandbox="allow-scripts"` only.** Its origin is opaque, so it cannot read the page, its cookies, its storage or `window.__hq`. It gets a small SDK (`hq`) whose calls are batched commands sent over a `MessageChannel`, set up by a handshake once the iframe's scripts have loaded. The page validates each batch (at most 512 commands, 30 batches a second, 32 sheets, 256 sprites, 8 buttons) and stops the plugin on that page if a batch breaks a limit.
- **Retained sprites, not immediate drawing.** The plugin says `loadSprite`, `spawn`, `moveTo`, `follow` or `setAnim`, and `PluginLayer` in `WorldView` moves and animates the sprites on the page's clock. `follow` reuses the built-in pets' trail following (`petFollow.ts`, now with a gap parameter and a rest spot beside the owner, away from their own pet, so two followers do not queue behind the owner). Sprites sort with avatars by their feet, and the page redraws only when one moves or changes frame, so render on demand ([0017](0017-movement-reconciliation-and-render-on-demand.md)) holds.
- **Wire:** `{"t":"plg","pl":<name>,"d":<json>}` in both directions (1500 bytes, 10/s, burst 20 from the client) and `{"t":"plgs"}` when the running set changes. HTTP: `GET /api/plugins`, `GET`/`PUT /api/admin/plugins[/{name}]`, plugin routes at `/plugins/<name>/api/<path>` (session required), the compiled browser code at `/plugins/<name>/client.js`, and assets at `/plugins/<name>/assets/<path>`, which are public and come from `public/` only.
- **Buttons** declared by plugins are drawn by React, so they get the house style, an accessible name and keyboard focus. Their labels are plain text from the plugin, a documented exception to the translation dictionary. [Decision 0023](0023-plugin-ui-and-app-tokens.md) turned this into anchors, a modal and components.
- **Pets are a plugin.** The built-in pet (an avatar field, decision 0012) is gone: one way to have pets, with more to it (several, names, colours, moods), costs less to maintain than two. The same species are drawn by the same code.
- **Settings an administrator makes.** A plugin declares them in `plugin.json` (`settings`: key, label, whole-number range, default); Home Quarters draws them in a modal behind the plugin's gear button in Administration > Plugins, checks and stores them per office (`plugin_settings`), audits each change, and the plugin reads `hq.settings()` and hears `onSettings()`. A plugin cannot draw its own interface in the admin dialog: the declared form is enough for the sample, and keeps that dialog Home Quarters'.
- **Hooks, not shared state.** A plugin exposes named functions (`hq.expose`) and others call them (`hq.plugins.call`), asynchronously, through the host: answers come back on a channel sized for every pending call, so two plugins calling each other never deadlock. The callee learns which plugin called and for which member, the member being set by Home Quarters from what the caller was handling, so a hook cannot be used to act for someone else. Images a plugin lets others draw live in `public/shared/`. The pets plugin uses this to walk pets other plugins draw (a plugin outside the repository can bring its own creatures) without opening its own settings or its members' pets to them.
- **The sample plugin** (`plugins/bundled/hq-pets`) lets members add pets: the built-in kinds and an original seedling, drawn by `web/src/game/art/pets.ts` and `sampleCreature.ts` and exported by `web/src/game/art/pluginPets.ts` to two PNGs, in their own colours and in light greys that `hq.setTint` colours. A member's pets walk in a line 20, 36, 52 px... behind and, at rest, potter about their owner's feet, close enough to fit at a desk (`follow`'s `gap`, `beside` and `roam`; the pottering is computed on each page from the sprite and the clock, so pages agree without a message, at the cost of redraws while a pet walks). Each can have a name, shown with its owner's on mouse hover while it wanders (`setLabel`). Wandering pets have moods that change about every 5 minutes (explore, near home, near the owner, along with another wandering pet), run by the owner's page and relayed by the server; every page walks them along paths around walls (`walkTo`, `follow` with a sprite). Pets are kept in `hq.kv`; the office's limit is its `limit` setting (3 by default, Administration > Plugins); each page draws at most 240 of its sprites, its own member's first, under the page's 256. Its interface (a settings modal, a Let wander / Call toggle) is described in [decision 0023](0023-plugin-ui-and-app-tokens.md). It shows the patterns authors should copy: changes are broadcast once per update, and browser messages are checked before use.

## Alternatives

- **Immediate-mode `draw()` every frame (PICO-8 or LÖVE style):** it would mean one iframe round trip per frame, and Chrome throttles hidden cross-origin frames. It would also undo render on demand.
- **A same-origin iframe or a module in the page, for synchronous calls:** the same origin grants the whole page (DOM, cookies, session, media), and a read-only object cannot hold that back. Trusted code would make it acceptable, but one bug could then break the office, and plugins would grow into Home Quarters' internals.
- **A Web Worker:** it has no DOM but shares the page's origin (cookies on fetch, IndexedDB), so it isolates less than an opaque iframe for the same messaging cost.
- **Lua (gopher-lua), the first version:** smaller and faster (about 16 µs for the sample's tick against 35 µs, `bench/plugin-runtime`), but untyped, without a heap cap, and a second language next to the browser's. Replaced before release, so nobody depends on it.
- **goja:** a mature pure-Go JavaScript engine, without the Go 1.27 requirement, but without a heap cap either.
- **Bun or Node in a separate process:** real npm and fast, but another runtime in the image, a process to supervise, an IPC hop per event, tens of MB per process, and full disk and network access.
- **WebAssembly (wazero, Extism):** the strongest sandbox and any compiled language, at the price of a build chain for every small plugin.
- **Keeping both Lua and TypeScript:** two bindings drift in small ways (null and undefined, empty tables, errors, a heap cap on one side only) and every API change, test and example is paid twice.
- **Kicking a slow client for plugin traffic, like other reliable frames:** that would let one plugin disconnect people. A dropped plugin frame is counted, and plugins resynchronise.

## Impact

- Performance: with plugins off, nothing changes (no host, no routes, no client work). With the sample plugin on, the server adds one goroutine and one QuickJS VM per plugin (about 0.45 MB each, measured with 50 members in `bench/plugin-runtime`) and a 10 Hz `update`; a sample tick with 5 messages costs about 35 µs. Compiling and loading took 3 to 4 ms for the sample and about 0.2 s for a synthetic 1 MB plugin. The page adds one hidden iframe and a 100 ms update message per plugin. An idle page with creatures standing drew 11 frames in 3 s in the `plugins` scenario (render on demand intact). No capacity measurement was made.
- Maintenance: `internal/plugin` is the only package that runs plugin code. `world.PluginFrame`/`OnPresence` are the only world entry points. `web/src/plugins` holds the iframe host, the SDK and command validation, and `web/src/game/pluginLayer.ts` does the drawing. The protocol, `docs/plugins.md` and the SDK change together.
- Install: optional. Set `HQ_PLUGINS_DIR`; the Docker image ships the bundled plugins at `/app/plugins/bundled`, and an operator's own go in `/app/plugins/installed`. New dependencies: `modernc.org/quickjs` v0.25.0 (BSD-3-Clause, QuickJS itself MIT) and `github.com/evanw/esbuild` v0.28.2 (MIT), about 10 MB of binary together. Go 1.27 is required (by modernc.org/quickjs), in `go.mod`, the Dockerfile and CI. New tables: `plugins` and `plugin_kv` (migration 009).
- Known limits: nothing outside the plugin can be awaited (no network or timers on the server). A compiled bundle is at most 256 KB (QuickJS parses within the heap cap). A compile error points at the plugin's TypeScript file, but a runtime error's line is the compiled code's. A page may hold up to 32 sheets of 2048 x 2048 px per plugin (about 512 MB of textures at the worst). Edits are picked up when a plugin is turned off and on again. Routes are fixed paths. There are no plugin modals or HTML panels yet. While moving to its resting spot, a creature can briefly cross the owner's pet.
